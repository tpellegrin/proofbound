## Composability
The retry loop (`notifications/retry.py:1-18`) and status mapping (`notifications/status.py:1-10`) were untouched — they remain pure, provider-agnostic logic. The `transport.post` seam is unchanged. However, `app.py` absorbed all provider-specific knowledge: endpoints, authentication schemes, and payload field mappings now live in the `PROVIDERS` dictionary (lines 9–34). This couples infrastructure configuration to the application entry point. Adding a third provider will require editing `app.py` again, and any code that wants to inspect or extend provider capabilities must import from `app.py`, which is not a configuration module.

## Domain alignment
Provider configuration (endpoints, credentials, request shapes) is an infrastructure concern, but it now resides in `app.py` — the application entry point whose purpose is wiring requests to the delivery pipeline. The `notifications` package owns retry policy and outcome vocabulary, yet knows nothing about providers. A new provider forces changes to `app.py` rather than extending a provider registry. The concept of "provider" has no dedicated owner; it is split between `app.py` (configuration) and the call to `retry.deliver_with_retry` (execution).

## Change locality
The diff touches only `app.py` (+35/−4 lines). For the immediate ask (one new provider), this is proportionate. But the locality was achieved by centralizing provider knowledge in the wrong module. Each future provider will expand the same `PROVIDERS` dictionary in `app.py`, making that file a growing configuration monolith. The change did not introduce a provider abstraction or registry, so the cost of the next provider is identical to the first — no marginal improvement in locality.
