## Composability
The change concentrates all provider-specific knowledge (endpoints, auth headers, payload field mappings) into `app.py`. Previously `app.py` only knew Acme; now it explicitly configures both providers in a `PROVIDERS` dict and contains two payload builder functions (`_acme_payload`, `_beacon_payload`). The `retry` module remains unaware of providers — it still receives only `(url, headers, payload)` — so the retry policy and transport seam stay composable. Tradeoff: adding a third provider requires modifying `app.py` again; provider configuration isn't pluggable without touching the composition root.

## Domain alignment
Provider configuration (endpoint, auth scheme, payload shape) lives in `app.py`, the application entry point. This is a reasonable ownership choice for a composition root — it wires providers together. The payload builder functions are provider-specific serialization logic co-located with their config, which keeps the mapping visible. The retry policy (`notifications/retry.py`), status code interpretation (`notifications/status.py`), and HTTP seam (`transport.py`) each retain their single purposes. No domain concept leaked into the wrong module.

## Change locality
The change touched only `app.py` (~30 lines added). `notifications/retry.py`, `notifications/status.py`, and `transport.py` are unchanged — the retry loop, outcome vocabulary, and transport contract were fully preserved. The scope is proportionate: the request was "add a second provider with different endpoint/header/payload," and the implementation added exactly that configuration in the one place that composes the notification call.
