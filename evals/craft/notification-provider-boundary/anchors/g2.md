## Composability

The change introduced a new dependency: `app.py` now imports `DEFAULT_PROVIDER` from `delivery`. Previously `app.notify` knew nothing about providers—it only constructed a `Notification` and called `delivery.send`. Now it must be aware of the provider concept and pass it through. The `delivery` module also gained a new responsibility: it now acts as a registry (`_senders` dict) that maps provider names to sender instances. This is a new concern (provider selection/registry) inside the delivery boundary that didn't exist before.

## Domain alignment

The "provider" concept sits awkwardly. It's a property of the notification request (per the task: "chosen per notification"), but it's not part of `Notification` in `notifications/model.py`—it's a separate parameter to `delivery.send`. The `DEFAULT_PROVIDER` constant lives in `delivery/__init__.py`, yet `app.py` imports it to use as a default argument. This leaks delivery-internal configuration into the application layer. A better alignment would keep the default entirely inside `delivery.send(notification, provider=None)` so callers don't depend on delivery's constants.

## Change locality

The reach was mostly proportionate: a new provider file (`delivery/beacon.py`), wiring in `delivery/__init__.py`, and the entry point in `app.py` accepting the new parameter. However, the change also required `app.py` to import a constant from `delivery`, creating a new cross-layer dependency that wasn't strictly necessary for the feature. The `Sender` protocol, `Notification` model, and `transport` seam were correctly untouched.
