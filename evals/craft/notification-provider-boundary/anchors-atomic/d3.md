## Composability

The registry pattern in `delivery/registry.py` keeps providers decoupled: each provider module registers a handler function on import, and `delivery/__init__.py` simply asks the registry for the named handler. This means adding Beacon required **no changes to Acme** and **no changes to the registry itself** — only a new module (`delivery/providers/beacon.py`) that self-registers.

However, `delivery/__init__.py` now explicitly imports both providers (`from delivery.providers import acme, beacon`) to trigger registration. This couples the delivery boundary to the *set* of available providers. If a third provider is added, `delivery/__init__.py` must be edited again to import it. The registry was designed so providers register themselves on import, but the boundary still needs to ensure those imports happen. A more composable design would use entry points or a plugin discovery mechanism so the boundary doesn't name providers at all.

The `app.py` change is minimal — it just threads the `provider` parameter through — which is appropriate for an entry point.

## Domain alignment

The provider-specific concerns (endpoint, headers, payload mapping, response interpretation) are correctly isolated in `delivery/providers/beacon.py`. The `Notification` model in `notifications/model.py` remains unaware of delivery mechanics, and the retry/attempt logic lives in the provider where it belongs (since providers may have different retry semantics).

One misalignment: the `MAX_ATTEMPTS` constant is duplicated in both `acme.py` and `beacon.py`. The accepted behaviour says "up to three attempts in total" as a *product-wide* policy, yet each provider redefines it. If the policy changes, every provider must be updated. This constant belongs in a shared policy module or the registry, not in each provider.

Also, `beacon.py` treats *any* non-200 status as `rejected` (line 22-23), but the acceptance criteria only specify that `400` maps to `rejected`. A `5xx` or network error should be retried per the "transport error is retried" rule. The current code would incorrectly treat a 500 as `rejected` and not retry. Acme's implementation correctly distinguishes 4xx (rejected) from other errors (retry).

## Change locality

The reach was proportionate: 
- **app.py**: +1 parameter, 1 line changed
- **delivery/__init__.py**: signature change + import line, 3 lines changed  
- **delivery/providers/beacon.py**: new file (~35 lines)
- **delivery/registry.py**: unchanged
- **notifications/model.py**: unchanged
- **transport.py**: unchanged

No changes leaked into the domain model or transport. The only non-local touch was the import list in `delivery/__init__.py`, which as noted above is a known limitation of the registry-as-import-side-effect pattern. For a "add a second provider" task, this is a reasonable tradeoff — the alternative (plugin discovery) would be premature infrastructure.
