## Composability

The change introduced provider-specific logic into `notifications/status.py`, which previously only interpreted HTTP status codes. Now `outcome_for()` must inspect the response body and branch on `provider` to handle Beacon's `result` field. This couples the status interpretation to provider details — it now knows Beacon uses `{"result": "accepted"}`, `{"result": "refused"}`, `{"result": "unavailable"}`. If a third provider reports outcomes differently (e.g., in headers, or with different JSON structure), `status.py` will grow more conditionals. The retry loop in `retry.py` also now threads the `provider` parameter through, though it doesn't use it directly — it passes it to `status.outcome_for()`. The transport layer remains correctly isolated.

## Domain alignment

The concept of "how a provider signals success/failure/retry" lives in `status.py`, which is appropriate — it's the translation layer between provider responses and the product's outcome vocabulary. However, the provider-specific payload field mapping (`to`/`channel`/`title`/`text` vs `recipient`/`kind`/`headline`/`message`) lives in `app.py`'s `PROVIDERS` config. This is a reasonable split: `app.py` knows the *shape* of each provider's request, `status.py` knows the *meaning* of each provider's response. The retry policy (3 attempts, no retry on rejection) remains in `retry.py` where it belongs.

## Change locality

The change touched three files: `app.py` (provider config + dispatch), `retry.py` (threading provider through), `status.py` (Beacon response interpretation). This is proportionate — adding a provider with different request/response conventions requires changes at the boundaries (request construction, response interpretation) and the plumbing between them. The transport layer was untouched. The main cost is that `status.py` now has an explicit `provider` branch; future providers will add more branches there unless the response interpretation is made data-driven (e.g., a `response_parser` per provider in the config).
