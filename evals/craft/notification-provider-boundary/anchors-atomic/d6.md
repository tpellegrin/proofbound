## Composability
The change required `app.notify` to accept and pass through a `provider` parameter, making the application layer aware of delivery providers. Previously `app.notify` only knew about the notification content; now it must know which provider string to forward. The delivery boundary (`delivery/__init__.py`) gained a hardcoded registry (`_senders`) and string-based dispatch, coupling it to concrete provider names. A new `delivery/beacon.py` was added (implied), which is expected, but the registry approach means adding a third provider requires modifying `delivery/__init__.py` again — the boundary absorbs provider enumeration.

## Domain alignment
The `Notification` model and `Sender` protocol remain clean — they don't know about providers. However, the *concept* of "which provider" now leaks into `app.py` (the caller) and `delivery/__init__.py` (the boundary). The provider string is a routing concern that arguably belongs in configuration or a factory, not in the application's notify signature. The delivery boundary now owns the mapping from provider name to sender instance, which mixes configuration with the delivery abstraction.

## Change locality
The change touched three files: `app.py` (signature change), `delivery/__init__.py` (registry + dispatch), and a new `delivery/beacon.py`. `delivery/acme.py` was untouched. The reach is mostly proportionate — adding a provider naturally requires a new sender implementation and wiring it in. However, the `app.py` change propagates the provider parameter to every caller of `notify`, which is wider than necessary if provider selection were handled internally (e.g., via configuration or per-user preference). The diff also doesn't show tests; if tests exist for `app.notify`, they would need updating for the new parameter.
