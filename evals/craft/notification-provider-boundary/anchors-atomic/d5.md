Based on the code and diff provided in your message, here's my analysis:

## Composability

The change required `app.py` to absorb a new concern: **provider selection**. Previously `app.notify` knew nothing about providers — it just forwarded a `Notification`. Now it must accept a `provider` parameter and pass it through. This leaks delivery-infrastructure concerns into the application layer. The `delivery/__init__.py` boundary also grew a registry (`_senders`) and a `DEFAULT` constant, making it aware of *which* providers exist — previously it only knew *one* sender. The `Sender` protocol in `delivery/sender.py` was untouched, which is good, but the composition root (`delivery/__init__.py`) now couples to concrete provider names.

## Domain alignment

The **provider identity** concept ("acme" vs "beacon") now lives in two places it doesn't belong:
- `app.py` — the application layer shouldn't know provider names
- `delivery/__init__.py` — the delivery boundary shouldn't be a registry of provider names

Provider identity is a **configuration/routing concern**, not an application or core delivery concern. It belongs in a separate routing or configuration layer. The `Notification` model correctly remains pure (no provider field), but the *choice* of provider is now threaded through the application call stack.

## Change locality

The reach was **disproportionate**. Adding one provider touched:
1. `app.py` — API signature change (all callers affected, even though default preserves behavior)
2. `delivery/__init__.py` — new registry logic, default constant
3. New `delivery/beacon.py` (implied)

A more local change would have kept `app.notify` unchanged and resolved the provider via configuration or a routing layer outside the application call path. The diff shows the change propagating "up" to the API boundary rather than being contained in the delivery subsystem.
