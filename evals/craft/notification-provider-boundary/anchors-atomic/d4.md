## Composability
The change weakens the registry's composability guarantee. `delivery/__init__.py` now explicitly imports `beacon` alongside `acme` (line 5), meaning every new provider requires modifying this central file. The registry pattern in `delivery/registry.py` was designed so providers self-register on import without the delivery boundary knowing their names — but `delivery/__init__.py` defeats that by hardcoding the import list. Future providers will need edits here, creating a central coupling point that the architecture tried to avoid.

## Domain alignment
The `provider` parameter leaks into `app.notify()` (the application layer), forcing callers to know provider identifiers (`"acme"`, `"beacon"`). The task states the provider is "chosen per notification," so this may be intentional, but it makes the application layer aware of delivery infrastructure taxonomy. The `Notification` model (domain concept) correctly stays clean — no provider field added there.

## Change locality
The reach is larger than necessary. Adding a provider with a different endpoint, header scheme, payload shape, and response protocol should only require a new provider module. Instead, the change also touches:
- `app.py` — adds `provider` parameter to public API
- `delivery/__init__.py` — adds parameter + explicit beacon import (defeating self-registration)
- (Unshown) `delivery/providers/beacon.py` — new provider implementation

The `delivery/__init__.py` edit is the avoidable expansion: if providers truly self-registered, importing `delivery.providers` (a package) or using entry-point discovery would keep the boundary closed to new providers.
