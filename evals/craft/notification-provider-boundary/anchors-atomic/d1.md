## Composability

The change introduced provider-specific knowledge into `notifications/status.py`, which previously only interpreted generic HTTP status codes. Now `outcome_for` contains a `provider == "beacon"` branch that parses Beacon's response body format (`result: "accepted" | "refused" | "unavailable"`). This means the status module has absorbed a provider-specific concern — interpreting a particular provider's response envelope — that it previously did not need to know about.

`notifications/retry.py` also had to accept and thread through a `provider` parameter it does not use itself, solely to pass it to `status.outcome_for`. The retry logic's purpose is attempt counting and backoff; it now carries a provider identifier as transitive plumbing.

## Domain alignment

Provider-specific response interpretation (how to map Beacon's `{"result": "..."}` to the shared outcome vocabulary) lives in `status.py`, a module whose stated purpose is "turn a provider response into a delivery outcome." But the *mapping rules* for a given provider are a property of that provider's integration, not a generic status concern. Acme's mapping (HTTP-status-based) is the implicit default; Beacon's mapping (body-based) is an explicit branch. A third provider would add another branch to the same function, growing a decision table that belongs to the providers, not the shared vocabulary.

Conversely, provider configuration (endpoints, headers, field names) correctly lives in `app.py` at the application boundary.

## Change locality

The change touched three files (`app.py`, `retry.py`, `status.py`) to add one provider. The reach extended into `retry.py` and `status.py` because the design threads the provider identifier through the call chain to a central interpretation function. A more localized design would encapsulate each provider's request-building and response-interpretation behind a small interface (e.g., `ProviderSpec` with `build_payload` and `interpret_response`), so adding a provider only touches the provider's own module and the registry in `app.py`. The current approach makes the next provider require edits to `status.py` and `retry.py` again.
