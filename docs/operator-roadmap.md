# Current roadmap: evidence before expansion

This is the current product route; the [historical implementation plan](architecture/specification-reflection-harness-implementation-plan.md)
retains design history. Capability tests establish mechanisms; regression tests protect known behavior.
Neither a larger test count nor more agent activity establishes product value.

| Milestone | User benefit | Missing evidence / success criterion | Reason to defer further scope |
|---|---|---|---|
| **Now: supervised goal-to-change** | Start, understand, resume and receive a reviewed change or precise blocker | Production path exercised offline; ordinary fresh live use and a frozen competent direct-agent comparison must complete, retaining every terminal outcome and quality alongside total effort | One environment/backend and one bounded change expose usability defects faster than another platform |
| **Next: repeated fresh comparisons and a second project change** | Preserve compatibility, dependencies and useful authority across handoff | Fresh tasks, followed by a second requirements change through the same project; measure defects, false acceptance/rejection, successful continuation, coordinator/worker/human effort | One paired task is diagnostic, not reliability or superiority evidence |
| **Then: durable accepted implementation binding and longer retention** | Accepted code remains traceable after run cleanup; recovery suits long projects | Demonstrate prevention of concrete authority-loss/recovery failures; derive architectural checks from accepted system constraints and measure caught defects | Adding provenance nobody consumes or checks without failures prevented adds cost without demonstrated benefit |
| **Conditional: more backends, review coverage, orthogonal falsifiers, selected formal checks, per-role routing and context/memory improvements** | Address an observed bottleneck | Each requires a measured failure/effort bottleneck, frozen falsifiable comparison and qualification on its own configuration | No plugins, adaptive swarms, model tournament or formal-verification framework in this milestone |

Grow a held-out task panel only when repeated outcomes make selection and calibration meaningful.
Track false acceptance and false rejection as well as completion. Do not select or retry tasks until
the workflow wins. Use the [canonical comparison rules](architecture/proofbound/evaluation-comparison.md).
See the [current dated observations](architecture/proofbound/evidence/supervised-workflow-2026-09-21.md).
